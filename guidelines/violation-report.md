## V-01

**Unnamed unique constraint on `users.email`**

| Field | Value |
| ----- | ----- |
| Guideline | [DB-09](database.md): "Unique constraints are given explicit names." |
| File | `backend/app/models/user.py`, and the generated migration |
| Generated by | Claude Code, task 1.2 |
| Found by | Reading the autogenerated migration before committing it (the review step required by DB-06) |

**What the AI generated.**

```python
# backend/app/models/user.py
email = db.Column(db.String(255), unique=True, nullable=False)
```

The migration then contained an unnamed constraint, next to the correctly named one on `board_members`:

```python
sa.UniqueConstraint('email')
sa.UniqueConstraint('board_id', 'user_id', name='uq_board_member')
```

**Why it matters.** PostgreSQL would name the constraint itself (`users_email_key`). A later migration that drops or changes it has to hardcode a database-generated name, which can differ on another database.

**Fix applied.**

```python
# backend/app/models/user.py
__table_args__ = (db.UniqueConstraint("email", name="uq_users_email"),)

email = db.Column(db.String(255), nullable=False)
```

The first migration had not been committed yet, so it was rolled back (`flask db downgrade base`), deleted and regenerated. The committed migration contains `sa.UniqueConstraint('email', name='uq_users_email')`.

**Note on the cause.** `unique=True` is the idiom every tutorial uses, and the design document's `User` model used it too, so the AI reproduced it. The guideline only caught it because DB-06 forces a read of the generated migration.

## V-02

**Board detail loaded its columns and cards twice, the second time one query per column**

| Field | Value |
| ----- | ----- |
| Guideline | [DB-07](database.md): "When a response includes related rows, load them in the same service call with `selectinload` or `joinedload`." |
| File | `backend/app/blueprints/boards/service.py`, `get_board` |
| Generated by | Claude Code, task 5.1 |
| Found by | Mutation-checking the query-count test: removing an eager load did not make the test fail, which led to counting the real statements |

**What the AI generated.** The code looks compliant. It has the `selectinload` chain the design asks for:

```python
membership = require_member(user_id, board_id)
db.session.scalars(
    select(Board).where(Board.id == board_id).options(
        selectinload(Board.columns)
        .selectinload(BoardColumn.cards.and_(Card.deleted_at.is_(None)))
        .selectinload(Card.assignee)
    )
).one()                      # result thrown away
return membership            # the route then reads membership.board.columns
```

**Why it matters.** The SQLAlchemy session holds only weak references. Nothing pointed at the loaded `Board`, so Python discarded it together with its columns and cards. When the route serialized `membership.board`, everything was loaded again lazily: one query for the board, one for its columns, then one per column for cards and one per assignee. A board with 5 columns sent 14 statements instead of 5, and the count grew with every column. The deleted-card filter was lost as well, because the lazy load does not apply it.

**Fix applied.**

```python
board = db.session.scalars(select(Board)...).one()
set_committed_value(membership, "board", board)   # keep the loaded board attached to the result
return membership
```

The request now sends exactly 5 statements (membership, board, columns, cards, assignees) for any board size. `test_get_board_uses_a_fixed_number_of_queries` asserts this.

**Note on the cause.** The first version of that test passed with the bug in place. The test's own fixtures still held the board, users and columns in memory, so the session answered from memory and the extra queries never ran. The test now empties the session before each measured request, as a real request would start, and uses two different assignees.

## V-03

**A card query repeated the soft-delete filter by hand instead of starting from `active_cards()`**

| Field | Value |
| ----- | ----- |
| Guideline | [DB-04](database.md): "Use the shared helper `active_cards()` as the starting point of card queries." |
| File | `backend/app/blueprints/cards/service.py`, `create_card` |
| Generated by | Claude Code, task 7.1 |
| Found by | Reading the finished service against DB-04, query by query |

**What the AI generated.** The query that finds the last card's order in a column:

```python
last_order = db.session.scalar(
    select(func.max(Card.order)).where(Card.column_id == column_id, Card.deleted_at.is_(None))
)
```

**Why it matters.** The result was correct, and a test (`test_new_card_goes_after_the_last_active_card`) proves deleted cards are ignored. The problem is the pattern: the filter is written by hand in one more place. The next aggregate copied from this one can drop `deleted_at.is_(None)` and still look reasonable in review. DB-04 exists so that there is a single place where "active card" is defined. The other four card queries in the same file already started from the helper; this one did not because it is an aggregate and `select(func.max(...))` is the usual way to write it.

**Fix applied.**

```python
last_order = db.session.scalar(
    active_cards().where(Card.column_id == column_id).with_only_columns(func.max(Card.order))
)
```

**Note.** This is the same guideline the agent missed in the before/after comparison ([`comparison/README.md`](comparison/README.md)). The one remaining hand-written `Card.deleted_at.is_(None)` is in `boards/service.py`, inside `selectinload(BoardColumn.cards.and_(...))`. A relationship load cannot start from a `select`, and DB-04 names that case explicitly, so it stays.

## V-04

**The notification list was cut off at the left edge on a 375 px screen**

| Field | Value |
| ----- | ----- |
| Guideline | [FE-08](frontend.md): "Layouts are written for 375 px first and widened with `sm:` / `md:` / `lg:`." |
| File | `frontend/components/notifications/NotificationBell.tsx` |
| Generated by | Claude Code, task 16.2 |
| Found by | Opening the list in a real browser at 375 x 812. The Jest tests, lint, typecheck and build had all passed |

**What the AI generated.** The list was positioned against the bell button, the desktop way:

```tsx
<div className="absolute right-0 mt-2 w-[min(22rem,calc(100vw-2rem))] ...">
```

**Why it matters.** `right-0` lines the panel up with the bell's right edge. On a phone the bell is not at the screen's right edge, because the "Log out" button sits beside it, so a 343 px panel started 76 px off-screen (measured: `left: -75.9`). The first words of every notification were unreadable. The width formula made the panel *fit* the screen, which is why it looked correct in the code; it was the anchor that was written desktop-first.

**Fix applied.** Mobile first: pinned to the viewport with a 16 px margin, and anchored to the bell only from `sm:` up.

```tsx
<div className="fixed inset-x-4 top-16 ... sm:absolute sm:inset-x-auto sm:right-0 sm:top-auto sm:mt-2 sm:w-88">
```

Measured after the fix at 375 px: `left: 16, right: 359`.

**Note on the cause.** No automated check in the project can see this. It is the reason every page is opened at 375 px before it is committed.

## V-05

**An inline `style` set the width of the analytics bars**

| Field | Value |
| ----- | ----- |
| Guideline | [FE-08](frontend.md): "Styling uses Tailwind classes. No inline `style={{}}` for layout." |
| File | `frontend/components/board/AnalyticsModal.tsx` |
| Generated by | Claude Code, board analytics panel |
| Found by | Searching the finished components for `style={{`, `fetch(`, `<button`, `process.env` and `any`, the patterns the frontend guidelines forbid outside named files |

**What the AI generated.** A bar per column, sized with an inline style:

```tsx
<span className="h-3 rounded-full bg-board">
  <span className="block h-3 rounded-full bg-action"
        style={{ width: `${(column.count / most) * 100}%` }} />
</span>
```

**Why it matters.** A width that depends on data cannot be a fixed Tailwind class, which is why the inline style looked like the only way. The two nested `<span>`s were also meaningless to a screen reader: a coloured bar with no value.

**Fix applied.** The native element for "how much of a maximum":

```tsx
<progress value={column.count} max={most}
          aria-label={`${column.column_name}: ${column.count} of the largest column's ${most}`}
          className="h-3 w-full appearance-none overflow-hidden rounded-full bg-board
                     [&::-webkit-progress-value]:bg-action [&::-moz-progress-bar]:bg-action ..." />
```

No inline style is left anywhere in `frontend/app` or `frontend/components`.

## V-06

**The whole board page scrolled sideways at 375 px, not just the board strip**

| Field | Value |
| ----- | ----- |
| Guideline | [FE-08](frontend.md): "The Kanban board is the only place that scrolls horizontally (`overflow-x-auto`)." |
| File | `frontend/components/board/KanbanBoard.tsx` |
| Generated by | Claude Code, task 18.5 |
| Found by | `e2e/responsive.spec.ts`, a Playwright test at 375 x 812 that compares the document's `scrollWidth` with its `clientWidth` |

**What the AI generated.** The strip has the class the guideline asks for:

```tsx
<div className="flex flex-1 items-start gap-3 overflow-x-auto px-4 pb-6">
```

**Why it matters.** With three columns the document was 890 px wide on a 375 px screen (measured: `html scrollWidth = 890`, `body scrollWidth = 375`). The columns themselves were clipped correctly. The overflow came from the screen-reader-only text inside each column header (`sr-only`, which is `position: absolute`). An absolutely positioned element is not clipped by a scroll container unless that container is itself positioned, so those 1 px spans sat at their columns' real off-screen positions and stretched the page. The page looked right in a screenshot and only moved when swiped.

**Fix applied.** `relative` on the strip, so its absolutely positioned descendants belong to it:

```tsx
<div className="relative flex flex-1 items-start gap-3 overflow-x-auto px-4 pb-6">
```

After the fix the test passes: the page does not scroll sideways, the third column is off-screen until the strip is scrolled, and then it is in view.

**Note on the cause.** The same page had been checked by hand in a browser one step earlier and reported as fine, with two columns at a 551 px width. It took three columns at a true 375 px to show it.
