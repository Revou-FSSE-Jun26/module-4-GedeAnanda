## V-01

**Unnamed unique constraint on `users.email`**

| Field | Value |
| ----- | ----- |
| Guideline | [DB-09](database.md): "Unique constraints are given explicit names." |
| File | `backend/app/models/user.py`, and the generated migration |
| Generated by | Claude Code, task 1.2 |
| Found by | Reading the autogenerated migration before committing it (the review step required by DB-06) |

**What the AI generated.**

```python
# backend/app/models/user.py
email = db.Column(db.String(255), unique=True, nullable=False)
```

The migration then contained an unnamed constraint, next to the correctly named one on `board_members`:

```python
sa.UniqueConstraint('email')
sa.UniqueConstraint('board_id', 'user_id', name='uq_board_member')
```

**Why it matters.** PostgreSQL would name the constraint itself (`users_email_key`). A later migration that drops or changes it has to hardcode a database-generated name, which can differ on another database.

**Fix applied.**

```python
# backend/app/models/user.py
__table_args__ = (db.UniqueConstraint("email", name="uq_users_email"),)

email = db.Column(db.String(255), nullable=False)
```

The first migration had not been committed yet, so it was rolled back (`flask db downgrade base`), deleted and regenerated. The committed migration contains `sa.UniqueConstraint('email', name='uq_users_email')`.

**Note on the cause.** `unique=True` is the idiom every tutorial uses, and the design document's `User` model used it too, so the AI reproduced it. The guideline only caught it because DB-06 forces a read of the generated migration.

## V-02

**Board detail loaded its columns and cards twice, the second time one query per column**

| Field | Value |
| ----- | ----- |
| Guideline | [DB-07](database.md): "When a response includes related rows, load them in the same service call with `selectinload` or `joinedload`." |
| File | `backend/app/blueprints/boards/service.py`, `get_board` |
| Generated by | Claude Code, task 5.1 |
| Found by | Mutation-checking the query-count test: removing an eager load did not make the test fail, which led to counting the real statements |

**What the AI generated.** The code looks compliant. It has the `selectinload` chain the design asks for:

```python
membership = require_member(user_id, board_id)
db.session.scalars(
    select(Board).where(Board.id == board_id).options(
        selectinload(Board.columns)
        .selectinload(BoardColumn.cards.and_(Card.deleted_at.is_(None)))
        .selectinload(Card.assignee)
    )
).one()                      # result thrown away
return membership            # the route then reads membership.board.columns
```

**Why it matters.** The SQLAlchemy session holds only weak references. Nothing pointed at the loaded `Board`, so Python discarded it together with its columns and cards. When the route serialized `membership.board`, everything was loaded again lazily: one query for the board, one for its columns, then one per column for cards and one per assignee. A board with 5 columns sent 14 statements instead of 5, and the count grew with every column. The deleted-card filter was lost as well, because the lazy load does not apply it.

**Fix applied.**

```python
board = db.session.scalars(select(Board)...).one()
set_committed_value(membership, "board", board)   # keep the loaded board attached to the result
return membership
```

The request now sends exactly 5 statements (membership, board, columns, cards, assignees) for any board size. `test_get_board_uses_a_fixed_number_of_queries` asserts this.

**Note on the cause.** The first version of that test passed with the bug in place. The test's own fixtures still held the board, users and columns in memory, so the session answered from memory and the extra queries never ran. The test now empties the session before each measured request, as a real request would start, and uses two different assignees.

## Review notes that are not guideline violations

These problems were found in the same reviews. They break no guideline, but they are recorded because each one changed the code.

| Where | Problem | Fix |
| ----- | ------- | --- |
| `backend/app/config.py` | A plain `postgresql://` URL makes SQLAlchemy 2.1 load the psycopg 3 driver, which is not installed (`ModuleNotFoundError: No module named 'psycopg'`). The design only planned for `postgres://` → `postgresql://`. | `normalize_database_url` rewrites both schemes to `postgresql+psycopg2://`. |
| `backend/tests/test_error_handlers.py` | Test-only routes were added inside a module-scoped fixture. That works only while this file runs before any other test file, because Flask rejects new routes after the first request. | The routes moved to `tests/probes.py` and are registered once in the `app` fixture, before any request. Verified by running the test files in both orders. |
| `backend/app/models/notification.py` | `passive_deletes=True` was set on the many-to-one side of `Notification.card` / `Notification.board`, where it has no effect. | Removed. The `ON DELETE SET NULL` on the foreign keys does the work. |
| `backend/app/blueprints/auth/service.py` | `register_user` trimmed the name *after* `RegisterSchema` had validated it, so a name of only spaces passed `Length(min=1)` and was stored as an empty string. | The trim moved into a `@pre_load` hook on `RegisterSchema`, so validation sees the trimmed value. Covered by `test_register_name_of_only_spaces_returns_400`. |
